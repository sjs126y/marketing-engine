## 4. 关键约定（别踩）

1. **新增表必须进分片配置**：`credit_*` 都在 `DB_ONLY_TABLES`（按 `user_id` 分库、不分表）。
   新表不加进去，路由会落到错误库或直接找不到表。
2. **对账的「批次剩余」不能按 `expires_at` 过滤**：到期未回收的批次仍在账户余额里。
3. **过期必须条件更新**：`update ... where id=? and user_id=? and state='active'`，否则多实例重复回收、账户被多扣。
4. **`credit_ledger.balance_after` 是 NOT NULL**：任何写流水的地方都要给真实余额（`expire` 曾经传 null，链路一跑就炸）。
5. **`consume` 的幂等目前是「唯一键报错」而不是「幂等成功」**：同一 `bizNo` 重放会抛 `DuplicateKeyException`。
   现在上游每次用随机 `bizNo`，碰不到；**P2 支付回调必须先把这里改成幂等返回上次结果**。
6. **演示开关**：`app.credit.demo-instant-expire`（ttlDays=-1）、`app.credit.admin-endpoints-enabled`（运营接口），生产必须关。
7. **签到**：积分只由主站发；中台发次数。不要再往 `daily_behavior_rebate` 加 sign/integral。

## 6. 面试口径（P1 版）

> **资产**：账户 + 批次 + 流水三张表，按有效期分批管理，消耗走 FIFO，到期按日分桶回收；三表同分片，一个本地事务覆盖。
> **运营**：过期扫描每小时 + 全量兜底，多实例靠条件更新幂等；对账三值比对，差异落表只暴露不修正。
> **可靠性**：发放幂等（event_id）、记账幂等（biz_no）、回调幂等（out_trade_no，P2）；上线前先把「流水必填字段」这类坑踩了一遍。

**两个可讲的取舍**：
1. 为什么对账不自动修？—— 自动修数会把「记账 bug」变成「数据被悄悄改过」，事后无法追溯；暴露 + 告警 + 人工决策。
2. 为什么签到不立刻按设计文档收敛？—— 抽奖次数还挂在 sku 返利上，硬删会丢功能；先掐积分双发，等次数迁进权益中心再彻底收敛。
3. 支付为什么要拆成「回调 + outbox + 异步发放」？—— 支付是外部事实、发放是内部动作，中间任何一环都可能挂；合在一起就只能二选一：要么丢钱，要么重复发。
4. 为什么对账要专门给「部分退款」开口子？—— 不退时净入账应等于应发数，部分退款后净入账等于已消耗部分；规则写死成「必须相等」，每次部分退款都会报假差异。

且消耗流水的第一条用 `bizNo` 本身，幂等判定走唯一索引精确命中。

**链路长相**：

```
下单(order_no 唯一) → 回调(out_trade_no 唯一 + 金额校验)
   → 订单 created→paid 与 outbox 同一事务 → MQ pay_grant
   → grant(eventId=pay:{orderNo}) 幂等入账 → 订单 paid→granted
```

**退款与三方对账已补齐**（V11）：退款按「该笔发放还剩多少」折算，冲正走批次 reversed + 账户扣减 + reverse 流水；
