# 权益中心改造方案（marketing-engine → 用户资产中心）

> 目标：把「营销中台」升级为「权益中心」——从"发奖工具"变成"用户资产的管理者"。
> 一句话定位：**主站管「用户是谁」，权益中心管「用户有什么」，运营后台管「怎么发」。**

---

## 一、定位与边界变化

| | 改造前 | 改造后 |
|---|---|---|
| 余额在哪 | 主站 `users.credit` / `users.llm_quota` | **权益中心** `credit_account` / `credit_batch` |
| 中台职责 | 判定 + 发放 + 回调主站入账 | **账户、批次、有效期、过期、发放、风控、对账** |
| 回调用途 | 所有发奖都要回调主站 | **只有"外部履约类"权益才回调**（实物 / 第三方券 / 会员） |
| 中台份量 | 一个发奖服务 | 用户资产中心 |

**分通道的判据**：能不能自己记账。

| 权益类型 | 记账方 | 通道 |
|---|---|---|
| 积分 / 对话次数（内部资产） | 权益中心 | **同步入账** |
| 实物 / 第三方券 / 会员（外部履约） | 外部系统 | **Outbox 异步回调**（幂等键 + 签名 + 退避 + 死信） |

## 二、目标架构

```
┌─────────────┐        ┌──────────────────┐        ┌─────────────┐
│ 主站 C 端    │        │ 权益中心（Java）  │        │ 运营后台     │
│ FastAPI     │◄──────►│ Spring Boot      │◄──────►│ Next.js     │
│ 登录/对话    │  HMAC  │ 账户·批次·流水    │  JWT   │ 活动/规则/看板│
└─────────────┘        │ 发放·风控·对账    │        └─────────────┘
                       └──────────────────┘
                          │        │        │
                       MySQL     Redis    RabbitMQ
                    (分片库)   (判定/扣减)  (内部事件)
```

**主站只是调用方之一**——未来接第二个 C 端（小程序/公众号）不用改权益中心。

## 三、新增数据模型（权益中心，均按 user_id 分片）

**分片策略：与现有 `user_*` 表同分片（2 库 × 4 表）**，这样"扣减账户 + 扣减批次 + 写流水"三张表落在同一分片，**一个本地事务就能覆盖**。

```sql
-- ① 账户：汇总
credit_account(
  user_id, balance, frozen,
  total_granted, total_consumed, total_expired,
  version,                 -- 乐观锁（可选）
  create_time, update_time
)

-- ② 批次：每笔发放一批，带有效期 ← 资产端的关键
credit_batch(
  id, user_id, event_id UNIQUE,   -- event_id 幂等键（来自发放方）
  scene,                          -- sign / task / lottery / invite / pay
  amount, remaining,
  granted_at, expires_at,
  state                           -- active / exhausted / expired / reversed
)

-- ③ 流水：append-only
credit_ledger(
  id, user_id, biz_no UNIQUE,     -- 业务唯一号（biz_no 防重复记账）
  batch_id, scene, delta,
  type,                           -- grant / consume / expire / reverse
  balance_after, create_time
)
```

**支付相关（P2 阶段）**

```sql
pay_order(
  order_no UNIQUE, user_id, sku, amount_cent, count,
  state,                          -- created / paid / granted / closed / refunded
  out_trade_no, paid_at, create_time
)
pay_callback_log(
  id, out_trade_no UNIQUE, raw, received_at   -- 回调幂等 + 留痕
)
```

## 四、接口变更

### 权益中心新增（对内 OpenAPI，API Key + HMAC + 时间戳）

| 接口 | 说明 |
|---|---|
| `POST /open/v1/credit/grant` | 发放：`{userId, scene, amount, bizNo, ttlDays, eventId}`，**幂等** |
| `POST /open/v1/credit/consume` | 消耗：`{userId, scene, amount, bizNo}`，**FIFO 扣批次** |
| `GET /open/v1/credit/balance` | 余额 + 即将过期提示 |
| `GET /open/v1/credit/records` | 流水分页 |
| `POST /open/v1/pay/order` | 下单（商品 = 次数包 / 积分包） |
| `POST /open/v1/pay/callback` | 模拟支付回调（幂等） |

**原有接口保留**：`/open/v1/sign`、`/open/v1/quota/recharge`、`/open/v1/activity/{id}`。

### 主站改造（`upstream-ai-app/app.py`）

| 当前位置 | 改法 |
|---|---|
| `users.credit` / `users.llm_quota` | 只保留"缓存展示"或直接删；权威数据在权益中心 |
| `POST /api/chat` 扣积分 | 改为调 `credit/consume` |
| `POST /api/sign` | 保持（内部转调 `/open/v1/sign`） |
| `GET /api/me` | 余额取自权益中心 `credit/balance` |
| `POST /webhook/award` | 保留，但只处理**外部履约类**；积分/次数改为同步入账 |
| `POST /api/recharge` | 改为"支付下单"入口（P2） |

## 五、业务闭环

```
免费侧：签到 → 抽奖次数 → 抽奖 → 积分 → 对话消耗
付费侧：下单 → 模拟支付 → 回调 → 发放（次数/积分）→ 抽奖/对话
风控侧：单用户日限额 · 活动日预算 · 超限熔断
结算侧：支付 / 订单 / 权益流水 三方对账
```

## 八、关键技术点（面试要讲的）

| 点 | 说法 |
|---|---|
| **FIFO 消耗** | 消耗按 `expires_at` 升序扣批次，用户先花快过期的；余额 = 各批次 remaining 之和 |
| **本地事务覆盖三表** | 账户 / 批次 / 流水同按 user_id 分片 → 同一分片 → 一个事务搞定 |
| **幂等两层** | `credit_batch.event_id`（发放不重复）、`credit_ledger.biz_no`（记账不重复） |
| **过期分桶** | 按 `expires_at` 建索引，每天只扫"今天到期"那一桶，不全表扫 |
| **内外事务分离** | 支付是外部事实，权益入账是内部动作，中间用 Outbox 隔开，不可能一个事务做完 |
| **回调幂等** | 支付平台会重复通知（微信 24h 内最多 8 次）→ `out_trade_no` 唯一 + 先查后处理 |
| **三方对账** | 支付流水 / 订单 / 权益流水 三方比对，差异定位到单号 |
| **保底会改变成本** | 保底是人为干预概率 → 用蒙特卡洛算"配置概率"和"实际成本"的差 |

## 九、不做的事（划清范围）

| 不做 | 理由 |
|---|---|
| 真接微信/支付宝 | 要商户号，演示讲"回调幂等"足够；用模拟回调 |
| 实物履约 | 与"权益中心"定位无关，最多留一个外部履约通道 |
| 多租户 | 当前只有一个主站，加了是过度设计 |
| 微服务拆分 | 现在是模块化单体，拆了只会增加解释成本 |

## 十、叙事连带调整

| 现在 | 改成 |
|---|---|
| 营销中台 / 权益中台 | **权益中心 / 积分与权益中心** |
| 上游业务系统 | **主站 / C 端应用** |
| 中台不持有资产 | **主站管用户是谁，权益中心管用户有什么** |
| 发奖 | **权益发放** |

**简历段落（三段式）**

> **资产**：账户 + 批次 + 流水三张表，积分按有效期分批管理，消耗走 FIFO，到期分桶回收。
> **发放**：签到、任务、抽奖、购买共用一套发放底座；能自记账的同步入账，需外部履约的走异步回调。
> **可靠性**：发放幂等（event_id）、记账幂等（biz_no）、回调幂等（out_trade_no）；对账暴露偏差。

## 十一、验收：一屏演示动线

```
注册 → 对话（积分 -5） → 签到（得抽奖次数） → 抽奖（得积分）
     → 余额与流水一致 → 购买次数包（模拟支付） → 到账
     → 造一个快过期批次 → 过期提醒 → 到期自动回收
     → 跑对账脚本 → 差异 0
```

**这一条动线跑通，项目就从"抽奖演示"变成"有资产、有交易、有结算的产品"。**
